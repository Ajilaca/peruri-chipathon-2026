# Fase 9c: inti ML-KEM-768 (`mlkem_core`): KeyGen_internal, Encaps_internal, Decaps_internal - test plan dan aturan lulus

Ditulis 2026-10-03, sebelum RTL 9c apa pun dan sebelum pengukuran 9c apa pun. Lingkup: `evidence/phase09/phase9_plan.md` blok 9c; `docs/ROADMAP.md` Fase 9 (konfigurasi C7-core); FIPS 203 Algoritma 16-18 (ADR 0031: pemeriksaan masukan Bagian 7.2 dan 7.3 tidak ada di RTL; ADR 0032: satu STOP per blok). Golden: `tb/golden/mlkem.py` yang tidak diubah (`ml_kem_keygen_internal`, `ml_kem_encaps_internal`, `ml_kem_decaps_internal`) dan vektor NIST ACVP yang dipin di `tb/vectors/acvp/` (hanya grup ML-KEM-768). Label: MEASURED, INFERENCE, ESTIMATE, NOT MEASURED, perhitungan tim. Matematika terkunci (C1).

## 1. Apa yang dibangun
- `rtl/mlkem/mlkem_core.sv`: pengendali, buffer, dan sub-blok. Antarmuka: `op_i` (0 KeyGen, 1 Encaps, 2 Decaps), `start_i` (diterima hanya saat idle), `busy_o`, `done_o` (satu pulsa); port host (`h_we_i`, `h_addr_i[11:0]` = region[11:10] dan word[9:0], `h_wdata_i[63:0]`, `h_rdata_o[63:0]` satu siklus setelah alamat; region 0 KB, 1 CB, 2 CB2, 3 RF) yang dipakai hanya saat idle (tulis saat sibuk diabaikan). Keacakan masuk sebagai data: `d`, `z` (KeyGen) dan `m` (Encaps) ditulis host ke register file sebelum `start_i`; keluaran ada di buffer dan register file (di bawah).
- Buffer (word 64-bit, byte k word w adalah byte 8w + k): KB 300 word (2,400 byte, layout `dk`: dk_pke di word 0 (144 word), ek di word 144 (148 word, rho-nya di word 288), H(ek) di word 292, z di word 296; untuk Encaps host menulis `ek` di word 144), CB 136 word (ciphertext c: masukan Decaps, keluaran Encaps), CB2 136 word (c' enkripsi ulang), RF 32 word = 8 register masing-masing 4 word: 0 d, 1 z, 2 m (m' di Decaps), 3 rho, 4 sigma / r / r', 5 K (K' di Decaps; shared secret dibaca di sini setelah Encaps dan Decaps), 6 K_bar, 7 H(ek).
- Sub-blok: mesin K-PKE 8d tidak berubah (`kpke_smp_top_s10`, VAR = 2 OVERLAP, STREAM_A = 1, OVERLAP = 1, NPOLY = 12, sponge C5 di dalamnya), codec 9a (`mlkem_pack`, `mlkem_unpack`) lewat dua modul task (`mlkem_ldpoly`: byte sebuah region -> unpack -> koefisien -> port host mesin; `mlkem_stpoly`: port host mesin -> pack -> byte sebuah region), pembungkus hash dan perbandingan 9b (`mlkem_hash`, `mlkem_fo_cmp`). Helper kecil baru: RAM word (`mlkem_ram`), serializer word-ke-byte, dan FIFO 4-dalam.
- Jadwal adalah mikro-program (ROM `rtl/mlkem/mlkem_ctl_rom.sv`, dibangkitkan oleh `scripts/build/gen_mlkem_ctl_rom.py` dari `tb/golden/mlkem_ctl_model.py`): operasi LDP / STP (polinomial antara region dan slot mesin, d = 1, 4, 10, 12), HST / HFD / HGT (mulai hash dengan mode dan panjang, umpan word dari region atau word konstan 0x03, simpan digest ke register), SDL (seed mesin <- register 3 dan 4), RUN (program mesin), WR32 / RD32 (4 word antara register dan KB), CMP (bandingkan CB dengan CB2 dan pilih K' atau K_bar ke register 5), END. Kode garis-lurus: tidak ada cabang, jumlah loop, atau alamat yang bergantung pada data. Panjang variabel tersisa hanya pada rejection sampling matriks A di dalam mesin (bergantung pada rho publik, seperti di 8d) dan tunggu handshake.
- Ketiga program (slot perangkat keras = slot logis - 9, seperti 8d): KeyGen: G(d || 3) -> rho, sigma; seed; KeyGen mesin; t_hat (slot 3-5) -> byte ek (d = 12), s_hat (slot 0-2) -> dk_pke (d = 12); rho -> ek; H(ek) -> dk; z -> dk. Encaps: H(ek); G(m || H(ek)) -> K, r; rho dari ek; t_hat (slot 7-9) dan polinomial pesan (slot 11, d = 1) dimuat; Encrypt mesin; u (slot 3-5) -> c1 (d = 10), v (slot 10) -> c2 (d = 4). Decaps: c1, c2, dan s_hat dimuat; Decrypt mesin; w (slot 10) -> m' (d = 1); G(m' || h) -> K', r'; J(z || c) -> K_bar; enkripsi ulang seperti Encaps dengan m' dan r' ke CB2; CMP.
- Reset: asinkron, active low, pada state kendali; memori dan register datapath tidak di-reset. Clock: satu domain clock. Tidak ada crossing domain clock.
- Tidak dibangun: pemeriksaan masukan FIPS 203 (ADR 0031), pembangkitan keacakan (masukan), antarmuka HPS (Fase 10).

## 2. Model golden lebih dulu
`tb/golden/mlkem_ctl_model.py` (baru, independen dari RTL) menjalankan mikro-program yang sama pada primitives golden yang tidak diubah, model codec 9a, model hash dan perbandingan 9b, dan model program K-PKE 8d (`kpke_smp_model`, OVERLAP). `tb/golden/tests/test_mlkem_ctl_model.py`: mikro-program mereproduksi setiap vektor ACVP yang dipin (keyGen 25, enkapsulasi 25, dekapsulasi 10 ML-KEM-768) dan fungsi `ml_kem_*_internal` yang tidak diubah pada masukan acak (seed tetap), termasuk ciphertext yang diubah satu bit, dan round trip KeyGen -> Encaps -> Decaps. Pembangkit ROM memeriksa bahwa setiap program berakhir di END dan semua field dalam rentang.

## 3. Kasus sudut
- ACVP: semua grup file yang dipin untuk ML-KEM-768 (grup dekapsulasi mencakup ciphertext yang dimodifikasi: implicit rejection). Kedua grup key-check tidak dijalankan terhadap RTL (ADR 0031).
- Cross-check acak (seed tetap): 20 KeyGen, 20 Encaps, 20 Decaps dengan ciphertext valid dan 20 dengan ciphertext diubah satu bit (posisi: byte pertama, byte terakhir, batas c1 / c2, acak).
- Rantai: KeyGen -> Encaps -> Decaps melalui RTL (shared secret sama; ciphertext Encaps melewati host sebagai byte).
- Protokol: start saat sibuk diabaikan; tulis host saat sibuk diabaikan; `op_i` yang berubah saat sibuk diabaikan; reset di tengah setiap operasi lalu operasi bersih; dua operasi beruntun (buffer operasi sebelumnya tidak bocor ke berikutnya: Decaps tepat setelah Encaps dengan kunci lain).
- Siklus konstan (tanpa stall host, ek tetap): siklus Decaps identik untuk ciphertext valid dan ditolak, untuk kunci rahasia berbeda dengan ek sama (dk_pke dan z diubah, H(ek) dijaga konsisten), dan untuk ciphertext berbeda; Encaps identik untuk m berbeda dengan ek sama. Siklus KeyGen hanya bergantung pada rho publik (sampling A); sebaran atas d vektor ACVP dilaporkan.
- Register shared secret tidak ditimpa setelah done (ditahan sampai start berikutnya).

## 5. Aturan lulus (ditetapkan sebelum mengukur; tanpa toleransi)
9c PASS hanya bila: 1. V1-V8 lulus di kedua simulator, 100% vektor ACVP yang berlaku lulus (bagian 3) dan setiap kontrol V7 gagal seperti disyaratkan; 2. V9: fit berhasil dan timing terpenuhi pada 40.000 ns di setiap seed; 3. jumlah sumber daya, Fmax (median Fmax slow corner terendah atas seed 1-6), dan tabel siklus dilaporkan sebagai MEASURED. Baris C7-core roadmap diisi dari file-file ini. Tanpa klaim tentang papan.

## 6. ESTIMATE yang ditulis sebelum mengukur (bukan pengukuran)
- Siklus (perhitungan tim, dari bagian MEASURED: mesin KeyGen 6,344, Encrypt 7,655, Decrypt 3,109; pack 389 / 325 / 261 dan unpack 387 / 323 / 259 siklus per polinomial untuk d = 12 / 10 / 4; hash 30 / 33 / 282 / 274; compare 137; ditambah beberapa ratus siklus overhead kendali dan akses RAM): KeyGen sekitar 9,500; Encaps sekitar 11,500 (H 282 + G 33 + 3 x 387 + 259 + 7,655 + 3 x 325 + 261 + overhead); Decaps sekitar 17,000 (load sekitar 2,400, Decrypt 3,109, store 261, G 33, J 274, enkripsi ulang sekitar 9,800, compare 137).
- Sumber daya (perhitungan tim, jumlah bagian MEASURED, kernel-only): mesin 10,993 ALM, 44 M10K, 26 DSP; pembungkus hash dengan perbandingan 6,745 ALM; codec 299 ALM dan 2 DSP; jadi sekitar 18,000 ALM ditambah register file (2,048 flip-flop dan multiplekser baca 32:1), memori (KB 19.2 Kb, CB dan CB2 masing-masing 8.7 Kb: beberapa M10K) dan pengendali: orde 20,000 ALM dari 41,910 di perangkat (sekitar 48 %), sekitar 50 M10K, 28 DSP. Fmax: diharapkan dekat bagian paling lambat, mesin (median 43.8 MHz di 8d), tidak diprediksi lebih tepat.

## 7. Tidak dicakup
Pemeriksaan masukan FIPS 203 (ADR 0031), grup ACVP key-check terhadap RTL, bukti formal inti, papan, antarmuka HPS, daya atau side channel, optimasi (waktu encode / decode berurutan dan tidak tumpang tindih dengan mesin; itu biaya terukur, bukan klaim).

## 9. Amandemen A2 (2026-10-04): bukti formal pengendali ditambahkan (menggantikan butir 6 A1 dan kalimat tentang formal di bagian 4)
Bagian 4 berkata tidak ada bukti formal inti yang direncanakan. Common RTL Gate (CRG-8) meminta properti formal untuk logika kendali dan alamat baru, jadi bukti pengendali ditambahkan setelah run verifikasi; aturan lulus bagian 5 tidak berubah dan tidak ada yang sudah terukur diubah.
1. Apa yang dibuktikan (`formal/phase09-integration/9c/mlkem_core_formal_top.sv`, `mlkem_core_safety.sby`, dijalankan oleh `formal/run/run_formal_phase9c.py`): dua salinan `mlkem_core` berjalan berdampingan dengan masukan kendali yang sama dan data berbeda (data host, isi memori dan register file, dan sinyal data stub). E1: setiap register kendali kedua salinan sama setiap saat, yaitu tidak ada state, program counter, counter, strobe, atau alamat memori pengendali yang bergantung pada data apa pun (bukti tingkat-kendali untuk "tidak ada cabang, alamat, atau hitungan yang bergantung rahasia", dengan handshake sub-blok yang identik); S1 state dan program counter dalam rentang; S2 `busy_o` persis "tidak idle"; S3 tidak ada yang menulis memori di state LDP, HFD, SDL, RUN, CMP, FETCH, DISP (host tidak dapat menulis saat sibuk); S4 strobe start terjadi hanya di DISP, paling banyak satu, untuk operasi mikronya sendiri; S5 port host mesin ditulis hanya di LDP dan port seed hanya di SDL; S6 alamat yang dibangkitkan pengendali sendiri (WR32, RD32, HGT, tulis CMPK, baca HFD dan RD32) tetap di dalam memori yang dialamatinya; S7 counter langkah dalam rentang.
2. Apa yang tidak dibuktikan: sub-blok adalah stub protokol (`stubs_9c.sv`: mesin, hash, perbandingan, dan kedua modul task; memori, register file, dan ROM adalah yang nyata), jadi bukti tidak menyatakan apa pun tentang internal mereka (9a dan 9b punya bukti sendiri; mesin punya bukti Fase 6 dan 8), tentang alamat yang dibangkitkan modul task (bergantung pada counter pack, unpack, dan byte yang dibuktikan di 9a), tentang liveness (bahwa setiap operasi selesai: ditunjukkan simulasi, tidak dibuktikan), atau tentang nilai data. E1 berlaku untuk handshake identik: di inti nyata sebuah handshake dapat bergantung pada data hanya lewat rejection sampling matriks publik di dalam mesin.
3. Kontrol dan keterjangkauan: NC-E1 (program counter bergantung pada satu bit data), NC-S3 (tulis host diterima di state LDP), dan NC-S4 (task store mulai bersama task load) masing-masing gagal di base case. Run cover (anti-vakum, sinyal bebas stub dideklarasikan `wire` setelah temuan 9b): `mlkem_core_cover.sby` (kedalaman 260) mencapai KeyGen selesai, Encaps selesai, dan satu word digest ditulis; Decaps selesai dan state CMPK butuh lebih dari 260 siklus bahkan ketika stub selesai seketika (dua hash 136 sampai 148 word), jadi keduanya dicakup run panjang terpisah `mlkem_core_cover_deep.sby` (kedalaman 480, `python3 formal/run/run_formal_phase9c.py deep`).
4. Temuan saat menulis bukti (teks properti, bukan RTL): run pertama gagal karena register yang dimuat di state FETCH dibandingkan sebelum dimuat; induksi lalu butuh invarian pendukung yang tercantum di top formal (state kendali stub sama di kedua salinan, state operasi yang berjalan cocok dengan opcode mikro-instruksi tersimpan, mikro-instruksi tersimpan sama dengan word ROM, word diminta = dikonsumsi + sedang terbang + ditahan); tidak ada properti yang dilemahkan.
