# Phase 9I item 4: loads behind the K-PKE engine (K4) — test plan and adoption rule

**Order of work, stated plainly:** the instruction of Jevan (chat 2026-10-04 about 23:15) was to run item 4 unattended until the morning. The RTL (`kpke_sched_smp4`, `kpke_smp_top_s10o`, `mlkem_ldpoly2o`, `mlkem_core4`, `mlkem_ctl_rom3`) and the first simulation of the whole core (ACVP, Verilator, one run) were written and run **before** this document was written; the document was written while the control runs and the Quartus project were prepared. The estimates in section 3 are the ones given in chat before the first run of `mlkem_core4` (Encaps about -660 and Decaps about -2,600 cycles, KeyGen unchanged; derived from the profile and the slot use of the engine programs). The rule of section 5 was written **before any Quartus compile and before the control runs** of item 4; it is not tuned to a result. Scope: ADR 0034 item 4 ("new variant of frozen Phase 6-8 files"), Batch 2. Baseline: **K3** (`../9s2b/`: `mlkem_core3` with `NTT_P6 = 1`, `NTT_AR = 1`). Labels: MEASURED, ESTIMATE, INFERENCE. Kernel-only static timing with virtual pins; not a board result.

## 1. Why (MEASURED: profile of K2, `../9s2/profile_k2_verilator.json`)
Per operation the controller spends (cycles, K2): KeyGen RUN 6,740 and STP 1,578; Encaps RUN 8,060, LDP 1,044, STP 1,052; Decaps RUN 11,177, LDP 2,871, STP 1,315. A load of one polynomial costs about 263 cycles for every `d` (one coefficient per cycle). The engine host port works only while the engine is idle, so every load and store is in series with the engine.
From the engine programs (`tb/golden/kpke_smp_model.py`, variant OVERLAP, hardware slot numbers): in the **encrypt** program t_hat (slots 7, 8, 9) is first used by operation 31 of 37 and the message polynomial (slot 11) by the last operation; in the **decrypt** program only slot 3 (the first ciphertext polynomial) is needed by the first operation (NTT), slots 4 and 5 by the second and third NTT, the secret slots 0, 1, 2 by the product, slot 10 by the last subtraction. So all loads except the first can run while the engine already computes.

## 2. Design (a new variant; the Phase 6-8 files and `mlkem_core3` are not edited)
1. **Loader with backpressure** `rtl/mlkem/mlkem_ldpoly2o.sv`: `mlkem_ldpoly2` plus the input `tb_wready_i`; a coefficient is written and taken from the unpacker only in a cycle with `tb_wready_i = 1` (the unpacker already has `coef_ready_i`). Tied to 1 it is `mlkem_ldpoly2`.
2. **Engine sequencer variant** `rtl/sched/kpke_sched_smp4.sv` (copy of `kpke_sched_smp.sv`, parameter `HOSTOV`): (a) a host write while a program runs is granted only in a cycle in which neither the sequencer nor a sampler beat writes the store (`tb_wready_o`); the host has the lowest priority; (b) interlock: an operation is not started (the sequencer waits in FETCH) while a slot it uses is marked in `ov_pend_i` (NTT, INTT, SMPN, SMPA: d; PWM, ADD, SUB: d, a, b; PWMS: d, b). Host reads while running are not possible (stores stay in series). Top `rtl/sched/kpke_smp_top_s10o.sv` forwards the two new ports.
3. **Controller** `rtl/mlkem/mlkem_core4.sv` (copy of `mlkem_core3.sv`) with two micro-operations: `RUNS prog mask` (start the engine program and continue; `mask` = the slots loaded behind it, written to the interlock register `pend_q`) and `RUNJ` (wait until the engine is done; the finish is remembered, so it is not missed while loads run). A completed load clears its bit in `pend_q`. The existing `RUN` stays (KeyGen). Requires `CODEC_W2 = 1`. ROM `rtl/mlkem/mlkem_ctl_rom3.sv`, generated by `scripts/build/gen_mlkem_ctl_rom3.py` from `tb/golden/mlkem_ctl_model3.py` (static checks `check_static3`).
4. **New programs:** KeyGen unchanged. Encaps: `BGS; RD32 rho; LDP 7; JN; G; SDL; RUNS(encrypt, {8, 9, 11}); LDP 8, 9, 11; RUNJ; STP ...` (H(ek) in the background behind RD32 and one load; it still has to be complete before G, so about 390 cycles stay visible). Decaps: `BGS; LDP 3; RUNS(decrypt, {4, 5, 0, 1, 2, 10}); LDP 4, 5, 0, 1, 2, 10; RUNJ; STP 10; JN; G; RD32; SDL; RUNS(encrypt, {7, 8, 9, 11}); LDP 7, 8, 9, 11; RUNJ; STP ...; CMP`. The order of the loads is the order in which the engine program uses them.
5. **Why it is constant time:** every wait is on a signal that depends on the loader (fixed length) and the engine (fixed length except the public rejection sampling of A); no control depends on a secret.
6. **Static checks** (`check_static3`): the checks of model2 on the new programs; between `RUNS` and `RUNJ` only `LDP`; the mask is exactly the set of loaded slots; every loaded slot is used by the engine program; no STP, SDL, RUN, hash, WR32, RD32, CMP or END between them; programs at most 64 words.

## 5. Adoption rule (fixed before any Quartus compile and before the controls)
K4 is **adopted** on top of K3 only if all hold:
1. V1-V7 pass as stated (any ACVP mismatch rejects it; a control that does not fail as required voids the claim).
2. Timing met at 40.000 ns at every seed 1-6 (the gate) and at 15.000 ns at every seed 1-6.
3. ALM median at most 20,000 (15 ns and 40 ns).
4. For Encaps and Decaps, t = cycles / median Fmax at 15 ns of K4 is lower than that of K3; for KeyGen (equal cycles) t is not more than 3 % above that of K3 (the difference is Fmax noise only).
5. The number of seeds met at 15 ns is reported; the median Fmax and the spread of K4 against K3 (77.555 MHz, six seeds of S2b, K3-15-s1..s6) are stated, and an Fmax drop larger than the spread of the seeds is called a drop.
Otherwise K4 is reported as not adopted. The result is a Proposed ADR. V8 not done does not reject K4 but is stated beside the adoption as a limit of the evidence.

## 6. Not in this step
No reads through the host port while the engine runs (stores stay in series), no overlap of stores with the engine, no change to the engine programs or to the arithmetic, no second sampler, no constraint below 15 ns, no board result. Constant time means cycle-count invariance only.
