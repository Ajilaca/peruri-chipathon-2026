# Phase 9c: the ML-KEM-768 core (`mlkem_core`): KeyGen_internal, Encaps_internal, Decaps_internal — test plan and pass rule

Written 2026-10-03, **before any 9c RTL and before any 9c measurement**. Scope: `docs/evidence/phase09-integration/phase9_plan.md` block 9c; `docs/ROADMAP.md` Phase 9 (configuration C7-core); FIPS 203 Algorithms 16-18 (ADR 0031: the input checks of Sections 7.2 and 7.3 are not in the RTL; ADR 0032: one STOP per block). Golden: the unmodified `tb/golden/mlkem.py` (`ml_kem_keygen_internal`, `ml_kem_encaps_internal`, `ml_kem_decaps_internal`) and the pinned NIST ACVP vectors in `tb/vectors/acvp/` (ML-KEM-768 groups only). Labels: MEASURED, INFERENCE, ESTIMATE, NOT MEASURED, perhitungan tim. The mathematics is locked (C1).

## 1. What is built
- `rtl/mlkem/mlkem_core.sv`: the controller, the buffers and the sub-blocks. Interface: `op_i` (0 KeyGen, 1 Encaps, 2 Decaps), `start_i` (accepted only when idle), `busy_o`, `done_o` (one pulse); a host port (`h_we_i`, `h_addr_i[11:0]` = region[11:10] and word[9:0], `h_wdata_i[63:0]`, `h_rdata_o[63:0]` one cycle after the address; regions 0 KB, 1 CB, 2 CB2, 3 RF) that is used only while idle (a write while busy is ignored). Randomness enters as data: `d`, `z` (KeyGen) and `m` (Encaps) are written by the host into the register file before `start_i`; the output is in the buffers and in the register file (below).
- Buffers (64-bit words, byte k of word w is byte 8w + k): KB 300 words (2,400 bytes, the layout of `dk`: dk_pke at word 0 (144 words), ek at word 144 (148 words, its rho at word 288), H(ek) at word 292, z at word 296; for Encaps the host writes `ek` at word 144), CB 136 words (the ciphertext c: Decaps input, Encaps output), CB2 136 words (c' of the re-encryption), RF 32 words = 8 registers of 4 words: 0 d, 1 z, 2 m (m' in Decaps), 3 rho, 4 sigma / r / r', 5 K (K' in Decaps; the shared secret is read here after Encaps and Decaps), 6 K_bar, 7 H(ek).
- Sub-blocks: the K-PKE engine of 8d unchanged (`kpke_smp_top_s10`, VAR = 2 OVERLAP, STREAM_A = 1, OVERLAP = 1, NPOLY = 12, C5 sponge inside), the codec of 9a (`mlkem_pack`, `mlkem_unpack`) through two task modules (`mlkem_ldpoly`: bytes of a region -> unpack -> coefficients -> engine host port; `mlkem_stpoly`: engine host port -> pack -> bytes of a region), the hash wrapper and the comparison of 9b (`mlkem_hash`, `mlkem_fo_cmp`). New small helpers: a word RAM (`mlkem_ram`), a word-to-byte serialiser and a 4-deep FIFO.
- The schedule is a micro-program (ROM `rtl/mlkem/mlkem_ctl_rom.sv`, generated by `scripts/gen_mlkem_ctl_rom.py` from `tb/golden/mlkem_ctl_model.py`): the operations LDP / STP (polynomial between a region and an engine slot, d = 1, 4, 10, 12), HST / HFD / HGT (hash start with mode and length, feed words from a region or the constant word 0x03, store the digest into registers), SDL (engine seeds <- registers 3 and 4), RUN (engine program), WR32 / RD32 (4 words between a register and KB), CMP (compare CB with CB2 and select K' or K_bar into register 5), END. **Straight-line code: no branch, no loop count and no address depends on data.** Variable length remains only in the rejection sampling of the matrix A inside the engine (it depends on the public rho, as in 8d) and in handshake waits.
- The three programs (hardware slot = logical slot - 9, as 8d): KeyGen: G(d || 3) -> rho, sigma; seeds; engine KeyGen; t_hat (slots 3-5) -> ek bytes (d = 12), s_hat (slots 0-2) -> dk_pke (d = 12); rho -> ek; H(ek) -> dk; z -> dk. Encaps: H(ek); G(m || H(ek)) -> K, r; rho from ek; t_hat (slots 7-9) and the message polynomial (slot 11, d = 1) loaded; engine Encrypt; u (slots 3-5) -> c1 (d = 10), v (slot 10) -> c2 (d = 4). Decaps: c1, c2 and s_hat loaded; engine Decrypt; w (slot 10) -> m' (d = 1); G(m' || h) -> K', r'; J(z || c) -> K_bar; re-encryption as Encaps with m' and r' into CB2; CMP.
- Reset: asynchronous, active low, on the control state; memories and datapath registers are not reset. Clocks: one clock domain. No clock-domain crossing.
- Not built: the FIPS 203 input checks (ADR 0031), randomness generation (inputs), the HPS interface (Phase 10).

## 2. Golden model first
`tb/golden/mlkem_ctl_model.py` (new, independent of the RTL) runs the same micro-programs on the unmodified golden primitives, the codec model of 9a, the hash and comparison models of 9b and the K-PKE program model of 8d (`kpke_smp_model`, OVERLAP). `tb/golden/tests/test_mlkem_ctl_model.py`: the micro-programs reproduce every pinned ACVP vector (keyGen 25, encapsulation 25, decapsulation 10 of ML-KEM-768) and the unmodified `ml_kem_*_internal` functions on random inputs (fixed seed), including ciphertexts changed in one bit, and a KeyGen -> Encaps -> Decaps round trip. The ROM generator checks that every program ends in END and that all fields are in range.

## 3. Corner cases
- ACVP: all groups of the pinned files for ML-KEM-768 (the decapsulation group includes modified ciphertexts: implicit rejection). The two key-check groups are **not** run against the RTL (ADR 0031).
- Random cross-check (fixed seed): 20 KeyGen, 20 Encaps, 20 Decaps with valid ciphertexts and 20 with a ciphertext changed in one bit (positions: first byte, last byte, c1 / c2 border, random).
- Chain: KeyGen -> Encaps -> Decaps through the RTL (shared secrets equal; the ciphertext of Encaps goes through the host as bytes).
- Protocol: start while busy ignored; host write while busy ignored; `op_i` changed while busy ignored; reset in the middle of each operation then a clean operation; two operations back to back (the buffers of the earlier one do not leak into the next: Decaps right after Encaps with another key).
- Constant cycles (no host stalls, fixed ek): Decaps cycles identical for a valid and for rejected ciphertexts, for different secret keys with the same ek (dk_pke and z changed, H(ek) kept consistent) and for different ciphertexts; Encaps identical for different m with the same ek. KeyGen cycles depend on the public rho only (sampling of A); the spread over the d of the ACVP vectors is reported.
- The shared secret register is not overwritten after done (held until the next start).

## 5. Pass rule (fixed before measuring; no tolerance)
9c is PASS only if: 1. V1-V8 pass on both simulators, **100% of the applicable ACVP vectors pass** (section 3) and every control of V7 fails as required; 2. V9: the fit succeeds and timing is met at 40.000 ns at every seed; 3. the resource counts, Fmax (median of the lowest slow-corner Fmax over seeds 1-6) and the cycle table are reported as MEASURED. The C7-core row of the roadmap is filled from these files. No claim about the board.

## 9. Amendment A2 (2026-10-04): formal proof of the controller added (supersedes item 6 of A1 and the sentence on formal in section 4)
Section 4 said that no formal proof of the core was planned. The Common RTL Gate (CRG-8) asks for formal properties of new control and address logic, so a proof of the controller was added after the verification runs; the pass rule of section 5 is unchanged and nothing already measured was changed.
1. **What is proved** (`formal/phase09-integration/9c/mlkem_core_formal_top.sv`, `mlkem_core_safety.sby`, run by `formal/run_formal_phase9c.py`): two copies of `mlkem_core` run side by side with the same control inputs and **different data** (the host data, the contents of the memories and the register file, and the data signals of the stubs). E1: every control register of the two copies is equal at all times, i.e. no state, program counter, counter, strobe or memory address of the controller depends on any data (the control-level proof of "no branch, address or count depends on a secret", given identical handshakes of the sub-blocks); S1 state and program counter in range; S2 `busy_o` is exactly "not idle"; S3 nothing writes a memory in the states LDP, HFD, SDL, RUN, CMP, FETCH, DISP (the host cannot write while busy); S4 the start strobes occur only in DISP, one at most, for their own micro-operation; S5 the engine host port is written only in LDP and the seed port only in SDL; S6 the addresses the controller generates itself (WR32, RD32, HGT, CMPK writes, HFD and RD32 reads) stay inside the memory they address; S7 step counters in range.
2. **What is not proved:** the sub-blocks are protocol stubs (`stubs_9c.sv`: engine, hash, comparison and the two task modules; the memories, the register file and the ROM are the real ones), so the proof says nothing about their internals (9a and 9b have their own proofs; the engine has its Phase 6 and 8 proofs), about the addresses the task modules generate (they depend on the pack, unpack and byte counters proved in 9a), about liveness (that every operation finishes: shown by the simulations, not proved), or about data values. E1 holds for identical handshakes: in the real core a handshake can depend on data only through the rejection sampling of the public matrix inside the engine.
3. **Controls and reachability:** NC-E1 (the program counter depends on a data bit), NC-S3 (a host write is accepted in the state LDP) and NC-S4 (the store task starts together with the load task) each fail in the base case. Cover runs (anti-vacuity, free stub signals declared `wire` after the finding of 9b): `mlkem_core_cover.sby` (depth 260) reaches KeyGen done, Encaps done and a digest word written; Decaps done and the state CMPK need more than 260 cycles even when the stubs finish at once (two hashes of 136 to 148 words), so they are covered by the separate long run `mlkem_core_cover_deep.sby` (depth 480, `python3 formal/run_formal_phase9c.py deep`).
4. **Findings while writing the proof (property text, not RTL):** the first run failed because a register that is loaded in the state FETCH was compared before it was loaded; the induction then needed the supporting invariants listed in the formal top (the control state of the stubs is equal in both copies, the state of a running operation matches the opcode of the stored micro-instruction, the stored micro-instruction equals the ROM word, words requested = consumed + in flight + held); no property was weakened.
